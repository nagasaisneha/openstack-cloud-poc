# Authoritative capability and acceptance matrix

Audit date: 2026-10-26. This is the authoritative requirements-to-implementation matrix for mandatory scope, including Octavia and maintained OpenStack in both final environments. Local proposed target: **Gazpacho 2026.1 via controlled upgrade of the existing WSL instance to Ubuntu 24.04, then Caracal → Epoxy → Gazpacho**. No upgrade execution authorized. Staging remains Hibiscus/Kolla 23/Ubuntu 24.04 candidate. See the [same-instance feasibility/upgrade plan](../architecture/maintained-release-migration.md) and [environment-specific policy](../../deployment/release-policy.json). Older task tables retain implementation history.

Classification applies to the stated implementation/evidence scope. A Caracal result is a preserved historical baseline and never final maintained-release acceptance. **No capability has final local Gazpacho or staging Hibiscus acceptance yet.** No complete customer workflow, migration, staging deployment or physical HA result is claimed.

Allowed classifications: **Implemented and verified**, **Implemented but unverified**, **Not implemented**, **Blocked by local hardware**, **Requires actual staging infrastructure**, **Explicitly out of scope**. Partial implementations use “Implemented but unverified”; missing acceptance is stated explicitly. Unit tests and documentation alone do not verify a deployed capability.

## Customer workflow gate

The required sequence is: **W01** admin creates customer/project/quota → **W02** customer logs in → **W03** network and real VM → **W04** attach/write/read volume → **W05** object store/retrieve → **W06** customer creates Octavia LB → **W07** two real application VMs receive VIP traffic → **W08** failed backend automatically excluded → **W09** recovered backend automatically rejoins → **W10** actual usage visible → **W11** reproducible demo bill visible → **W12** admin sees usage/health → **W13** cross-tenant requests denied → **W14** all owned resources safely cleaned up. Browser requirements and original AI/recovery/security requirements remain additional acceptance; this sequence does not waive them.

Current result: **all-step workflow NOT PASSED**. Historical Caracal component results remain preserved; every step must be observed on the maintained final release. After convergence, traffic tests use fresh connections and verify actual backend response markers as well as Octavia state; a reported API status alone cannot pass distribution or health recovery.

## Audit evidence and gaps

Source baseline reviewed: `8ecabe0`, with a concurrent user README expansion preserved. Review covered requirements/task definitions, architecture image and architecture/acceptance records, source adapters/billing/fixtures, live acceptance scripts, Horizon templates, Kolla lock/inventory/preflight and CI. Current host service/listener inventory was read outside the restricted shell. Authenticated current catalog, provider inventory and protected report reinspection could not be performed because sudo requires the operator's password. Package presence/service state are observations, not new functional acceptance. Historical provider PASS claims in this matrix identify their original task record and release explicitly.

Security observations requiring follow-up: SSH and PCP monitoring/archive ports listen on wildcard IPv4/IPv6 addresses; the host also has a wildcard Apache port-80 listener. Binding alone is not proof of external reachability. Earlier operator Windows firewall output showed disabled profiles; current Windows policy and intended-client reachability require fresh verification. No firewall or listener configuration was changed during this audit.

Repository status, docs or offline test counts cannot pass the release gate. Root-only report data, credentials, private keys, guest data and billing records stay outside Git. No staging infrastructure or physical HA test was executed.
