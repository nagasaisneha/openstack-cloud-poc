# Service migration checkpoints for the existing cloud

Reviewed 2026-10-27. **Assessment and isolated component proof only; no OS/cloud upgrade authorized or run.** Source inventory and eight-schema recovery are recorded in [recovery evidence](../evidence/recovery-progress-2026-10-26.json). The [single execution checklist](../poc-completion-checklist.md) controls status.

Proposed same-instance checkpoints: **J1 Jammy/Caracal → N1 Noble/Caracal → E1 Noble/Epoxy → G1 Noble/Gazpacho**. Each checkpoint needs a matched, externally preserved rollback point and real regression acceptance before the next. A source-version SQL restore does not exercise any target migration. No package-only supported end-to-end route is claimed while Swift runtime ownership and other gates remain unresolved.

Common stop conditions: unsupported dependency graph, unrehearsed recovery, unknown schema/flag state, package-hook listener exposure, identity/data drift, insufficient capacity or failed integration test. Preserve failed evidence. Recovery restores software and data together; neither SQL downgrades nor broker reset is an approved rollback.

Full acceptance at N1/E1/G1: existing IDs/allocations and payload hashes preserved; scoped Keystone auth; core service health; retained VM start/stop/SSH/KVM; image/network/metadata/SG checks; owned Cinder write/read/snapshot/clone; Swift hash/isolation; trusted TLS/browser; application history and meter lineage; logs/alerts and backup checks. Final G1 full scope adds all customer steps, ingress/LB/health, complete metering/billing, AI, security and automation. Local results do not pass staging gates.
