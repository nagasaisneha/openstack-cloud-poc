# Existing WSL cloud: maintained-release upgrade decision

Reviewed 2026-10-27. **Planning only; execution is not authorized.** This supersedes the earlier fresh-target recommendation. Retain the existing WSL distribution, repository, configuration, identities, resources, data and backups. Do not create another POC, Linux VM, host or WSL distribution. Kolla remains a separate staging design; its host matrix is not the support test for this Ubuntu-package cloud.

## Feasibility and proposed target

There is **no verified supported Ubuntu Cloud Archive (UCA) package path to Gazpacho while keeping Ubuntu 22.04 unchanged**. Signed public metadata was checked, not just directory names. At review, `jammy-updates/gazpacho/InRelease` identifies itself as **jammy-updates/caracal**; it must not be used as Gazpacho. `jammy-updates/epoxy/InRelease` returned 404. Noble Epoxy, Flamingo and Gazpacho indexes passed UCA signature, release-identity and package-index SHA256 checks. Gazpacho OVS/OVN dependencies require `libc6 >= 2.38` and `libssl3t64`; this host has libc 2.35 and `libssl3`. Mixing Noble packages into Jammy, replacing libc independently, or changing system Python is not a supported solution.

The smallest **proposed OS bridge for the verified core packages** is an OS upgrade of the **same WSL instance to Ubuntu 24.04**, first retaining Caracal, then upgrading through **Caracal → Epoxy → Gazpacho**. No reinstall or resource recreation is the default. Ubuntu documents [same-instance WSL LTS upgrades](https://documentation.ubuntu.com/wsl/stable/howto/upgrade-ubuntu/) with WSL2/systemd. [Ubuntu 24.04 ships Caracal](https://documentation.ubuntu.com/release-notes/24.04/), giving an OS/cloud checkpoint before changing OpenStack series. This is a feasible design based on documented component paths, **not a validated whole-cloud upgrade or vendor certification of this custom WSL deployment**.

Upstream [2025.1 runtime testing](https://governance.openstack.org/tc/reference/runtimes/2025.1.html) includes an Ubuntu 22.04 Caracal-to-Epoxy upgrade job. Therefore newer OpenStack code is not intrinsically impossible on Jammy. That test does not supply UCA packages or a supported conversion of this installed package cloud to a source deployment. A source/backport/framework conversion would need a separate compatibility and maintenance case; it is not the smallest supported package change.

## Backup and rollback gates — not yet satisfied

Historical core isolated restore, service cycle and WSL restart PASS records remain valid for their original scope. They are **not** a fresh whole-environment pre-upgrade recovery point. The earlier seven SQL schemas and core guest recovery must be extended for Cinder, Swift, Horizon/TLS, application/billing state and a whole-WSL rollback. The operator has now supplied fresh protected source API inventory, actual eight-schema/three-OVSDB isolated restore PASS and actual job-journal backup/restore PASS. These scoped results do not establish full storage/billing or WSL boot recovery; see [T47](../tasks/T47.md) and [recorded summaries](../evidence/recovery-progress-2026-10-26.json).

1. Inventory and hash exact package versions/origins/holds, service units/drop-ins, config ownership, certificates/keys, private auth, all SQL schemas/grants, database migrations, broker definitions/queues/feature flags, OVSDB schemas, VM disk backing chains, Cinder image/LVM, Swift data/rings/xattrs, application DBs/ledger and Git SHA/diff. Keep secrets and resource identifiers in protected operator storage, never Git.
2. Review a maintenance window, stop/resume ownership and pending jobs; obtain explicit approval before quiescing guests/services. Create a consistent SQL/application/broker/storage snapshot. Use database-native/SQLite backup mechanisms and supported OVSDB snapshots, not raw live database-file copies. Record guest disk and volume/object content hashes at the consistency point.
3. Copy verified recovery artifacts **outside this WSL filesystem**. During the approved cold window, obtain a whole-instance export and a reviewed Windows/VHDX backup. Record checksums, WSL registration/version/default-user information and restoration instructions. Enough space inside the virtual ext4 disk does not prove enough free space on the Windows backup volume.
4. Verify restoration and representative VM, volume, object and ledger contents using matching source tools in isolation. Temporary isolated restore processes/files are recovery tests, not a second POC. They still need exact resource/capacity approval. No second Linux host/VM/distribution is the default test requirement.
5. Establish a **tested same-instance OS rollback** before changing the OS. [Microsoft's export/import commands](https://learn.microsoft.com/en-us/windows/wsl/basic-commands) create backups, but import/import-in-place register a distribution, and unregister permanently deletes it. An export alone is not proof of a safe same-instance restore. Resolve the supported offline VHDX/Windows restoration method and any separately required recovery approval. Never unregister the current distro as an automatic rollback step.

Rollback means restore a **matched checkpoint of OS/packages/config + SQL + broker + OVSDB + disks/objects + application ledger**, then run its acceptance tests. Do not downgrade migrated packages/schemas, reuse old broker data with arbitrary versions, or merge conflicting ledger writes. Stop on checksum mismatch, failed restore, unsupported dependency, drift, resource exhaustion or failed acceptance. Preserve failed-state evidence and all original backups. No backup pruning is authorized.

## Acceptance and remaining decisions

At **each** J1/N1/E1/G1 checkpoint: authenticate existing scoped identities; compare resource IDs/counts/roles/quotas/catalog and placement allocations; boot/start/stop the retained VM via Nova; verify KVM, SSH, DHCP/metadata/routing/SG denials; retrieve image hashes; attach an owned Cinder volume, write/read, detach, snapshot/restore and compare content; Swift scoped PUT/GET/hash/denial/delete; verify API/TLS/listener restrictions; compare ledger/rate/audit history and meter lineage; check logs/failed units, health and cleanup. Preserve all pre-existing assets. Record failures, exact release/package identities and measured recovery time.

Final acceptance also requires trusted admin/customer browser workflows, routed VM/VIP ingress, real two-backend traffic distribution, monitor-driven failed-backend exclusion and recovery, storage/network/compute usage, reproducible demo billing, tenant quotas/denials, monitoring/alerts and representative recovery. Existing Caracal PASS records cannot certify Gazpacho; fixture/offline tests cannot certify live cloud behavior. Physical HA and actual staging gates remain separate.

**Decision requested at planning level:** prefer Gazpacho on Ubuntu 24.04 in the existing WSL instance. **Execution status:** not authorized, not started, and not yet ready for an upgrade approval request. Upstream Swift runtime maintenance acceptance/live cutover, broker data/feature-flag/package review, full protected cold recovery and tested same-instance rollback remain genuine blockers. Signed artifacts, extracted runtimes and source SQL/jobs restore have scoped proof; they do not close those gates. If Ubuntu 22.04 must remain absolutely unchanged, there is currently no verified supported package upgrade satisfying the maintained final-release requirement.
