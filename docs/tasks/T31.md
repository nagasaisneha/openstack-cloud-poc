# T31 — Billing domain and immutable statement model

**Status:** Partial — offline billing domain and immutable statement ledger implemented; Keystone/browser integration remains pending

## Objective and scope

Implement an offline, provider-independent billing domain core that accepts trusted usage samples, applies explicit Decimal rates, and stores statement snapshots by project. This task does not create a meter source, HTTP endpoint, UI, or payment integration.

**Dependencies:** T29–T30.  
**Mapped requirements:** Project-level billing; distinct allocation/measurement/charge; currency/rounding; history after deletion; visible simulated/provisional data; backend role checks.  
**Planned files:** `openstack_cloud_poc/billing.py`, `tests/test_billing.py`, this record, and related billing semantics in the goal audit.

## Acceptance criteria

- [ ] Rate cards are versioned and effective-dated; amounts use finite non-negative `Decimal` values and an explicit currency/minor-unit precision.
- [ ] Usage units must match exactly; quantities and charges are never calculated with binary floating point or implicit conversion.
- [ ] UTC billing periods use `[start, end)` boundaries. Samples crossing an effective-rate boundary are rejected or mark the statement incomplete rather than being charged at an invented rate.
- [ ] Statements are aggregated by project, not user. Opaque resource IDs and source/rate version snapshots remain after cloud resource deletion.
- [ ] Line rounding uses `ROUND_HALF_UP` at configured currency precision; statement total is the sum of rounded lines.
- [ ] Missing coverage/rates yield a visible provisional/incomplete statement and never silently become zero usage.
- [ ] Project billing readers can retrieve only projects for which the trusted authorization adapter grants the billing role; cloud administrators can inspect all projects. Unauthenticated/unknown roles deny by default.
- [ ] Fixture samples remain `simulated`; an offline test cannot claim observed cloud usage.
- [ ] Statement records have append-only application semantics; corrections add a revision rather than rewriting the old record.
- [ ] Focused unit tests cover boundaries, role denial, precision, rate changes, provenance, idempotent versioning, and resource-independent history.

## Verification and limitations

Implemented `openstack_cloud_poc/billing.py` and `tests/test_billing.py`. The domain rejects float rates, enforces UTC billing windows and exact metric/unit matches, prevents overlapping effective rates, calculates with `Decimal`/`ROUND_HALF_UP`, retains opaque resource IDs, marks missing coverage/rates provisional with no fabricated total, and preserves observed versus simulated provenance. `BillingLedger` stores versioned rate cards and immutable SQLite statement snapshots with update/delete rejection triggers and append-only revisions. `BillingService` checks its supplied authenticated principal and role bindings before source or ledger reads.
