# T31 — Billing domain and immutable statement model

**Status:** Complete for the offline billing domain; provider metering and browser integration are separate tasks

## Objective and scope

Implement an offline, provider-independent billing domain core that accepts trusted usage samples, applies explicit Decimal rates, and stores statement snapshots by project. This task does not create a meter source, HTTP endpoint, UI, or payment integration.

**Dependencies:** T29–T30.  
**Mapped requirements:** Project-level billing; distinct allocation/measurement/charge; currency/rounding; history after deletion; visible simulated/provisional data; backend role checks.  
**Planned files:** `openstack_cloud_poc/billing.py`, `tests/test_billing.py`, this record, and related billing semantics in the goal audit.

## Acceptance criteria

- [x] Rate cards are versioned and effective-dated; amounts use finite non-negative `Decimal` values and supported currency/minor-unit precision (INR, USD, EUR, GBP, JPY).
- [x] Usage units must match exactly; quantities and charges are never calculated with binary floating point or implicit conversion.
- [x] UTC calendar-month periods use `[start, end)` boundaries. Samples crossing an effective-rate boundary make the statement provisional rather than charging at an invented rate.
- [x] Statements are aggregated by project, not user. Opaque resource IDs and source/rate version snapshots remain after cloud resource deletion.
- [x] Line rounding uses `ROUND_HALF_UP`; the statement total is the sum of rounded lines.
- [x] Missing coverage/rates yield a visible provisional statement without a final total; missing usage is never silently treated as zero.
- [x] Billing readers retrieve only projects for which the trusted authorization context grants `billing_viewer`/`project_admin`; only `cloud_admin` can inspect all projects or configure rates. Unauthenticated/unknown roles deny by default.
- [x] Fixture samples remain `simulated`; an offline test cannot claim observed cloud usage.
- [x] Rate cards and statements have append-only semantics. Identical recalculations return the existing statement; changed usage/rates append a revision.
- [x] Focused unit tests cover boundaries, role denial, precision, rate changes, provenance, idempotent replay, and resource-independent history.

## Verification and limitations

Implemented `openstack_cloud_poc/billing.py` and `tests/test_billing.py`. The domain rejects float rates, enforces UTC calendar-month windows and exact metric/unit matches, prevents overlapping effective rates, calculates with `Decimal`/`ROUND_HALF_UP`, retains opaque resource IDs, marks missing coverage/rates provisional with no fabricated total, and preserves observed versus simulated provenance. `BillingLedger` stores versioned rate cards and immutable SQLite statement snapshots with update/delete rejection triggers, idempotent fingerprints, and append-only revisions. `BillingService` checks its supplied authenticated principal and role bindings before source or ledger reads.

Tests use a temporary private SQLite DB and synthetic samples; a provider-shaped sample is only a data fixture, not a cloud observation. No Keystone authentication, real meter collection, application-server trust boundary, browser workflow, DB recovery, or bill reconciliation was exercised. `BillingPrincipal` must be constructed only by a trusted adapter; this module is not an HTTP authorization endpoint.
