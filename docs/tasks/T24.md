# T24 — Sample AI workload

**Status:** Blocked — no approved model/runtime artifact and no verified VM GPU path

## Scope and current evidence

T23 is complete only as a feasibility assessment: a historical CUDA-container probe saw an RTX 2060 with 6 GB VRAM, while host NVML failed and Nova guest passthrough remained unverified. No exact container image tag or model artifact was preserved. This work did not repeat the probe, download a model, access user data, configure a GPU, or create an OpenStack resource.

The current release goal requires the workload to produce a real inference result with reproducible resource evidence. A synthetic Python calculation would not meet that criterion. There is no selected model/license, pinned runtime image, model source, data-handling approval, or verified guest device path in the repository evidence.

## Acceptance and staging validation requirements

- [ ] Select a small model and review its license, provenance, checksum, and data classification.
- [ ] Pin a maintained runtime/container image by digest; scan it and retain an SBOM.
- [ ] First establish a bounded CPU baseline with explicit RAM, CPU, timeout, and disk limits.
- [ ] Test CUDA only where the approved host/container can access the device; record GPU model, VRAM peak, runtime, latency, and errors.
- [ ] Treat Nova PCI passthrough as a separate staging capability; validate scheduling, device ownership/isolation, quota, reset behavior, and tenant denial before offering it.
- [ ] Never infer H100/MIG or multi-tenant GPU isolation from RTX 2060 container visibility.
- [ ] Preserve input/output evidence without customer data; clean only workload-owned artifacts.

No AI workload acceptance is claimed. Local sample inference requires choosing an artifact and model source; guest GPU acceptance additionally requires the independently approved staging hardware and passthrough design.
