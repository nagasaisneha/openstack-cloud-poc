# T41 — Reproducible staging and operations

**Status:** Partial — staging deployment package and host preflight exist; target, approvals, deployment and operational acceptance remain unselected

## Objective and scope

Deliver a separately deployable staging configuration and operator handover for the browser-ready platform. The current Ubuntu 22.04/Caracal WSL installation is preserved and is not upgraded in place.

**Dependencies:** T30–T40; Gate 0 target/owners/budget and Gate 1 architecture/security approvals.
**Mapped requirements:** Reproducible deployment, HTTPS, secret management, monitoring/security checks, backup/restore, troubleshooting, resource constraints, separation of local and staging evidence.

## Acceptance criteria

- [ ] Staging host/network/storage topology is selected and approved; Kolla versions, container images and configuration are pinned and reproducible.
- [ ] Preflight checks capacity, host compatibility, interfaces, storage, DNS/NTP/MTU, secrets, operator/change ID and optional-service decisions; deployment fails closed on missing gates.
- [ ] Browser URL is HTTPS with managed certificate; user/admin secrets and service credentials are externalized, access-controlled and rotatable.
- [ ] Monitoring covers login, API/provisioning errors, worker/meter freshness, billing completeness, capacity, backups and security signals with actionable alerts.
- [ ] Backup/restore includes Horizon custom code/config, application DB, rate cards, statements, audit history, telemetry metadata and OpenStack resources as applicable; isolated restore is demonstrated.
- [ ] Startup, shutdown, upgrade, rollback, recovery, credential rotation, billing reconciliation and troubleshooting runbooks are reviewed by a named operator.
- [ ] Staging repeats T40 independently. Local results are not reused as staging evidence.
- [ ] Payment collection and tax-compliant invoicing remain explicitly separate unless independently scoped and implemented.
