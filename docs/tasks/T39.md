# T39 — Horizon billing and audit experience

**Status:** Partial backend slice — role-checked CSV, billing-action audit events and a unit-tested Keystone session adapter exist; Horizon and real usage remain undeployed

## Objective and scope

Add custom Horizon panels for account/project overview, roles, quotas, allocated and measured usage, pricing, itemized project statements, downloads and administrator cross-project comparison. Record auditable user/admin actions in backend code.

**Dependencies:** T32–T33 and T37–T38.
**Mapped requirements:** Account information; authorized projects/roles/quotas; usage and bills; admin pricing; tenant billing visibility; audit logs and downloadable statements.

## Implemented server-side export slice

`BillingService.project_statement_csv` returns a deterministic UTF-8 CSV only after the existing project billing-role check succeeds. Schema version 2 includes statement period/status, source, collection time, provenance, explicit incompleteness reason codes, rate version, per-resource quantities/rates/charges, and the statement total. Provisional statements keep a blank total; simulated data remains labelled. Formula-like text cells are apostrophe-prefixed for spreadsheet safety. A foreign statement ID is looked up only within the authorized project and returns the same not-found error as an unknown ID.

Verification: `PYTHONDONTWRITEBYTECODE=1 python3 -m unittest discover -s tests -p 'test_billing.py' -v` — 39 focused tests passed, including export contents, repeatability across collection timestamps, formula escaping, role denial before ledger access, foreign-statement non-disclosure, corrupt-history failure, and billing audit behavior. This is a service-level slice only; there is no HTTP download route, Horizon panel, or request layer to propagate correlation IDs. A Nova usage source now supplies observed but always-incomplete batches; it is not a billing-grade meter feed.

## Keystone session principal adapter

`KeystoneBillingPrincipalAdapter` invalidates and refreshes the server-side Keystone SDK session before constructing a principal. It matches the token user and selected project against trusted server context. It maps only explicit `billing_viewer`, `project_admin`, and project-scoped `billing_collector` roles plus the system-scoped `cloud_admin`/`billing_collector` roles; generic `member`, `reader`, or `admin` names do not grant billing access. `NovaBillingUsageSource` requires the same server-side SDK session to be project-scoped to the requested project and hold the explicit `billing_collector` role before it calls Nova. This code path is unit-tested but the live Nova policy/account role has not been configured or verified.

Verification: `PYTHONDONTWRITEBYTECODE=1 python3 -m unittest discover -s tests -p 'test_keystone_billing_auth.py' -v` — 10 tests passed for scope mapping, identity/project mismatch, unscoped and contradictory contexts, sanitized auth failures, and service-level cross-project denial. The adapter has not been connected to a Horizon request or exercised against live Keystone; its session must come from trusted server-side authentication code.

## Billing audit slice

The protected billing SQLite ledger now stores append-only audit events for rate-card configuration/read, statement generation/list/read/export, administrator statement listing, and audit-log reads. Records contain actor ID, project ID where applicable, fixed action name, target ID only on success, outcome, UTC timestamp, and a UUID correlation ID. Success events for rate changes and statement generation are committed in the same SQLite transaction as the rate/statement write. Denied and not-found reads are recorded without retaining the caller-supplied target ID. SQLite triggers reject event updates/deletes, and only `cloud_admin` can read the audit list through `BillingService`.

Verification: `PYTHONDONTWRITEBYTECODE=1 python3 -m unittest discover -s tests -p 'test_billing.py' -v` — 39 focused tests passed, including admin-only audit reads, denial records, correlation fields, ledger reopen persistence, update/delete rejection, corrupt-history failure, and rollback when audit persistence fails during rate or statement writes. This is not a complete application audit system: login, provisioning, identity/role/quota changes are not connected; database backup, retention, restore, and tamper evidence are not yet validated. No audit UI or live Horizon/Keystone integration exists.

## Acceptance criteria

- [ ] Tenant screens show only the signed-in user's data and authorized projects; usage and charges are keyed by project, with billing visibility restricted by explicit project role.
- [ ] The backend revalidates Keystone-derived project scope and role before every read/download or pricing mutation. Forged project IDs and foreign statement IDs are denied with non-disclosing errors.
- [ ] Users can see allocated capacity, measured meters, source/freshness/provenance, calculated charges, rate units, and provisional gaps as separate fields.
- [ ] Authorized project billing users download a stable CSV/JSON statement; resource deletion does not break prior downloads.
- [ ] Administrators configure effective-dated rates and compare usage/statements for all authorized tenant projects.
- [ ] Audit records include authenticated actor, project, action, target resource, outcome, UTC timestamp and correlation ID for login/access, provisioning, role/quota changes, rate edits, statement generation and downloads.
- [ ] Audit records exclude passwords, tokens, private keys, auth headers, and sensitive request bodies; retention/backup is documented and tested.
