## Selected local approach and dependency order

1. Run the protected preflight below. Require authenticated catalog observations, free proposed ports, no conflicting Swift assets, safe storage parents, package candidates, active memcached and current capacity. Its conservative initial setup guards require at least 1.5 GiB available RAM, 12 GiB free on the image filesystem and 4096 free inodes. These are deployment guards, not measured Swift capacity guarantees; repeat observations immediately before installation.
2. Inspect actual Ubuntu Caracal package contents and installation hooks; prevent wildcard service autostarts while installing. Retain configuration backups and a root-only journal. Reuse existing Keystone and memcached without replacing them.
3. Create one new task-owned 8-GiB filesystem image under `/var/lib/swift-poc`, using a free loop device discovered without disturbing Cinder's `/dev/loop0`. Format only that newly created, verified image as ext4, verify xattr write/read on it, mount it below `/srv/swift-poc`, and keep Swift's mount checks enabled. Existing paths, signatures, mounts or unowned loop attachments must stop setup. This bounded backend avoids filling the host filesystem through unbounded object writes. It shares the laptop's failure domain and is not independent durable storage.
4. Configure real Swift proxy/account/container/object services and rings with one device and one replica. Bind the proxy to `127.0.0.1:8080` and backend services to `127.0.0.1:6200–6202`. Use one worker per service initially; tune only from observed resource use. Generate Swift hash secrets and the service password into protected host files. Use Keystone `authtoken`/`keystoneauth`, project accounts and explicit member/operator roles. Do not grant a tenant reseller-wide access. Store no plaintext secret in a template, command argument, Git file or printed report.
5. Verify service health, exact listeners and the authenticated `object-store` API, then run the acceptance criteria below. Follow with core regression observations and extend metering, monitoring and backup coverage in their dependent tasks.

This is a laptop-specific functional deployment, separate from the maintained-release staging design. Swift supports filesystems with extended attributes; upstream recommends XFS for storage performance and reliability. The ext4 choice is a POC compatibility decision requiring an actual xattr probe and object integrity tests. Keystone integration follows the upstream `authtoken`/`keystoneauth` model. Sources: [Swift storage prerequisites](https://docs.openstack.org/swift/2024.1/install/storage-install-ubuntu-debian.html), [Swift Keystone authentication](https://docs.openstack.org/swift/2024.1/overview_auth.html). Package-specific behavior must be checked locally; old OS examples in the upstream install guide are not the staging target.

## Implemented preflight

Files: [`inspect_swift_readiness.py`](../../scripts/local-openstack/inspect_swift_readiness.py) and [`test_swift_readiness.py`](../../tests/test_swift_readiness.py).

Run in the actual Ubuntu terminal:

```bash
sudo /usr/bin/python3 -B /home/sneha/projects/openstack-cloud-poc/scripts/local-openstack/inspect_swift_readiness.py
```

The helper holds the existing POC lock, reuses protected root credentials and writes a new mode-protected sanitized `swift-readiness-*.json` report under `/root/openstack-poc-acceptance`. It observes packages/candidates, service units, listener counts, storage path presence/permissions, filesystem type, memory, free bytes and inodes. It authenticates to Keystone and checks the internal `object-store` catalog entry. An existing endpoint receives an account HEAD only when its URL exactly matches the current project's proposed loopback account; redirects and unexpected endpoints are refused. It records no tokens, passwords, endpoint URLs, project IDs, container names, object contents or raw exception text.

- Exit **0**, `ready_for_guarded_setup`: initial observations support the next guarded setup step. No xattr write, filesystem creation, package installation, service change or object acceptance has occurred.
- Exit **2**, `blocked_prerequisites` or `review_existing_state`: capacity/authentication/other prerequisites failed, or existing assets/listeners need inspection before reuse. An unavailable catalog lookup is not treated as verified endpoint absence.
- Exit **1**: inspection incomplete; read the sanitized failure category and protected report. No deployment or test resources are created by this helper.

Protected runtime output is pending from the operator. The assistant cannot read the root-only credentials or live reports directly.
