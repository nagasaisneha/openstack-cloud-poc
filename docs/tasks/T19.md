## Operator setup attempt and directory correction — 2026-10-26

The operator's first setup attempt used installer commit `b33daf96063ba69873377bbc4443ff2447965d6d` and reported **packages: PASS**, **filesystem: PASS**, then `unsafe_directory_metadata` during `mount_and_xattrs`. This was a historical failure; the guarded correction below was later run, and subsequent output confirmed mount/xattrs and Keystone setup passing. The protected journal and formatted image remain assets to preserve.

The cause is an installer defect: the process sets `umask(077)`, then `mkdir(mode=0755)` produces a mode-0700 directory, which the original helper rejects. A disposable local reproduction confirmed `requested=0755 actual=0700`. The first affected call creates `/srv/swift-poc`; the original separate mountpoint creation and later service drop-in directories had the same defect. The corrected helper applies the exact requested mode through an open directory descriptor only when it has just created that directory. Existing directories with unexpected ownership, type or permissions still fail without a chmod. Directory guard errors now include the affected path and expected/observed modes.

For this recorded partial attempt, run:

```bash
sudo /usr/bin/python3 -B /home/sneha/projects/openstack-cloud-poc/scripts/local-openstack/configure_swift.py \
  --readiness-report /root/openstack-poc-acceptance/swift-readiness-88a78b63e32544d2a5327489674867cf.json \
  --repair-umask-directory
```

The explicit resume option requires an existing protected setup journal. Before changing permissions it validates the recorded pre-mount failure and completed package/filesystem steps, the original protected preflight's absent `/srv/swift-poc` observation, the retained image's ownership/size/filesystem UUID, lack of image attachment or an existing mount/unit, and an empty root-owned directory with the expected mode. It records the inode, evidence digest and correction intent before applying mode 0755 to that single directory through its descriptor. An interrupted correction is accepted only with its recorded inode and unchanged evidence; an already completed correction performs no further chmod. Nonempty directories, symlinks, unexpected owners, differing evidence or existing mounts stop the correction.

The normal existing-journal path then verifies the installed packages and retained filesystem before proceeding. Do not remove the image or journal, rerun formatting manually, reset task state, or apply a recursive chmod/chown.
