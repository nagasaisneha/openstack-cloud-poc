# T33 — Keystone administration, projects, roles, and quotas

**Status:** Blocked — requires verified Horizon/Keystone browser path (T32)

## Objective and scope

Provide an administrator workflow to create/disable two test projects and users, assign project roles, set compute/network quotas, and control which verified services appear. Use Keystone and service policy as the authority; browser controls are not authorization.

**Dependencies:** T32.
**Mapped requirements:** Admin project/user/role/tenant administration; quota and service control; credential separation; backend role enforcement.

## Acceptance criteria

- [ ] A cloud administrator can create two isolated test projects and one separate user per project through the browser.
- [ ] Each user receives only the intended project membership and minimum role; admin credentials/session are separate from tenant credentials.
- [ ] Compute and network quota changes are confirmed against provider responses and obey reviewed capacity ceilings.
- [ ] Tenant resource requests exceeding quota fail with a sanitized, actionable error and no resource is misreported as created.
- [ ] Direct backend/API requests enforce identity, project scope, and role even when a user bypasses or forges UI actions.
- [ ] A project-level `billing_viewer` assignment is explicit; individual users do not become billable tenants.
- [ ] Positive/negative tests cover unknown/disabled users, insufficient role, project mismatch, and admin-only actions.
- [ ] Cleanup removes only task-created test identities/projects after evidence capture; the existing admin project and retained VM are preserved.

## Live-change gate

Before creating projects/users or changing quotas, record the exact names/IDs, roles, quota values, capacity/cost impact and cleanup plan. Use protected credentials and never print passwords or tokens.
